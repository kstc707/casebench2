# 02 · The scikit-learn track

## Goal
Give a student five real bugs from scikit-learn's history to fix in the browser. For each one they read
what it teaches and what the real fix was about, edit the "before" version of one scikit-learn file, and
run scikit-learn's own tests on their change. When every required test passes, the task counts as solved,
and the path shows it.

The plan is `docs/plans/section-1-scikit-learn-track.md` (10 steps). The decisions behind it are in
`.claude/team/decisions.md` (2026-10-11).

## Where we started
- The repo held only the dev team and the librarian (build log 01). There was no app.
- The researcher had shown, in Node (JavaScript outside a browser), that 10 of 10 real merged scikit-learn
  fixes behave as needed: their tests fail on the old code and pass with the fix.
- Nobody had yet tried it in a real browser. That was the biggest risk, so it was checked first.

**Terms used below:**
- **Pyodide**: Python compiled to run inside a web browser. It ships ready-made packages, including
  scikit-learn 1.8.0, NumPy, SciPy and pytest. Nothing runs on a server: the student's own browser runs
  the tests.
- **Web worker**: a background thread in the browser. Python runs there, so the page stays responsive
  while tests run. A *module* worker is the modern kind; Pyodide needs it.
- **SHA-256 pinning**: SHA-256 turns a file into a 64-character fingerprint. Change one byte and the
  fingerprint changes. We write the expected fingerprint into our code and refuse any file that doesn't
  match, so nobody can swap in a different file unnoticed.
- **fail→pass** (`failToPass`): tests that fail on the old code and pass with the real fix. They prove
  the bug is fixed.
- **pass→pass** (`passToPass`): tests that pass both before and after. They prove the fix didn't break
  anything else.
- **Mutation testing**: deliberately breaking the code (for example, deleting a safety check) and seeing
  whether any test notices. If every test stays green, the tests don't really protect that line.
- **CI** (continuous integration): checks GitHub runs automatically on every pull request.
- **localStorage**: a small key-value store the browser keeps for each website, on that device only.

## What we built

**The five tasks** (in suggested order, smallest real fix first):

| PR | Task folder | File the student edits | Required tests (fail→pass + pass→pass) |
|---|---|---|---|
| #33127 | `weighted-percentile-zero-weight` | `sklearn/utils/stats.py` | 1 + 86 = 87 |
| #33643 | `reconstruct-patches-full-size` | `sklearn/feature_extraction/image.py` | 4 + 22 = 26 |
| #33176 | `stratified-group-kfold-too-many-splits` | `sklearn/model_selection/_split.py` | 2 + 224 = 226 |
| #34815 | `fetch-file-plain-filename` | `sklearn/datasets/_base.py` | 10 + 39 = 49 |
| #33362 | `empty-pipeline-dir` | `sklearn/pipeline.py` | 1 + 140 = 141 |

**Content** (`content/scikit-learn/`):
- `sources.json`: the seed list. For each task: PR number, merge commit, and the 1.8.0 base.
- Per task, `content/scikit-learn/<slug>/`:
  - Generated by the builder: `task.json` (the test lists), `before/` (the 1.8.0 file), `tests/` (the
    PR's test file), `solution/` and `fix.diff` (the real fix), `tests.diff` (the PR's change to the
    test file).
  - Written by hand: `about.json` (title, what it teaches, our summary, quotes, where to look).
  - `source.md`: the upstream text the quotes come from, made by `apps/web/scripts/make-sklearn-sources.py`
    from a scikit-learn clone, with URLs and the fetch date.
- `LICENSE`: scikit-learn's BSD-3 license.

**Scripts** (`apps/web/scripts/`):
- `prepare-pyodide.mjs`: downloads the Pyodide 314.0.7 release once and refuses it unless its SHA-256
  matches. It extracts 23 files (5 core files and the 18 packages scikit-learn, its tests and pytest
  need), checks each against its own SHA-256, and puts them in `apps/web/public/pyodide/314.0.7/`.
- `build-sklearn-tasks.ts`: the **builder**. It applies each real fix to the 1.8.0 file, runs the whole
  test file before and after, and writes the task folder. It refuses a task with no fail→pass test, any
  test failing after the fix, a test skipped on one side only, or a patch that doesn't apply cleanly.
  The rules are in `apps/web/lib/sklearn/taskRules.ts`.
- `check-sklearn-tasks.ts`: the **checker** (CI). It re-runs every task from scratch and fails if
  anything differs from what the content claims (details under "Problems found").
- `runner-worker.mjs`: the module web worker that starts Python in the browser.

**The test runner** (`apps/web/lib/runner/`):
- `runner.py`: the Python side. It writes the student's file over the installed scikit-learn file and
  clears every `sklearn` module from memory. Then it runs exactly the requested test ids and always puts
  the original file back. It turns pytest's output into a clear result.
- `runner.ts`: runs the same `runner.py` from Node, for tests and CI.
- `useTestRunner.ts` and `pendingRuns.ts`: the browser side. They start the worker, allow one run at a
  time, and enforce the time limits (60 s for the issue's tests, 120 s for "Check my fix", then Python
  restarts).

**The pages** (`apps/web/app/`, Next.js):
- `page.tsx`: home, with one card and "N of 5 solved".
- `scikit-learn/page.tsx`: the path. The 5 tasks with what each teaches, the file, and a status (Not
  started / In progress / Solved).
- `scikit-learn/[slug]/page.tsx` with `components/task/TaskWorkspace.tsx`: the task page.
  - Left: what it teaches, the real context with quotes, where to look ("Jump to it"), and the tests.
  - Right: a code editor (CodeMirror) and a read-only tab with the test file.
  - Two buttons: "Run the issue's tests" and "Check my fix". Only "Check my fix" can mark a task
    solved.
  - After solving: "Solved. Checked in your browser.", the real fix and a link to the PR.
- `lib/progress.ts`: progress and drafts in the browser's localStorage. A blocked or corrupt store
  means "start fresh", never a crash.
- `lib/sklearn/runReport.ts`: decides "solved" and turns errors into plain sentences ("Your file has a
  syntax error on line 192: expected ':'").

**CI** (`.github/workflows/ci.yml`): a second job, `tasks`, downloads Pyodide (cached by its SHA-256),
runs the Pyodide tests and runs the checker.

**End-to-end check**: `apps/web/e2e/sklearn-track.mjs` drives the real app in headless Chromium.
It's run by hand.

**The risk check**: `research/sklearn-browser-spike/` (step 1), a throwaway page that proved
scikit-learn's tests run in a browser worker before any app code was written.

How the parts connect is in `docs/how-it-works.md`.

## Decisions and why
- **Run tests in the student's browser (Pyodide), not on a server.** It's free to run and needs no
  accounts. It reuses Casebench 1's approach. *Rejected for now:* a server sandbox. It's the long-term
  answer for trusted grading and for Hugging Face, but it's a bigger build.
- **Check the riskiest thing first.** Step 1 ran one task in a real browser before any app code.
  The plan said: if it fails, stop and ask the owner.
- **Self-host Pyodide, pinned by SHA-256.** *Rejected:* loading it from a CDN (a public file server
  like jsDelivr). This sandbox blocks jsDelivr, and a CDN file could change under us. *Also rejected:*
  installing from PyPI. Pyodide's own pytest 9.0.2 is used.
- **Two buttons.** "Run the issue's tests" is fast (2.5–5.3 s in the risk check) for trying changes.
  "Check my fix" runs every required test (about 30–32 s for #33176's 226 tests) and is the only way
  to solve.
- **Write the student's file over the installed scikit-learn file, then put the original back.** The
  tests import scikit-learn the normal way, so this is the simplest way to make them see the edit.
- **Commit the real fix.** It lets CI prove each fix passes without cloning scikit-learn. The fix is
  public on GitHub anyway. *Rejected:* Casebench 1's way of leaving it out, where CI could not prove the
  task was solvable.
- **Keep generated and hand-written files apart.** Rebuilding never overwrites our words.
- **Check every quote word for word** against the saved `source.md`, so the context can't be invented
  (`apps/web/lib/sklearn/about.test.ts`).
- **Progress in localStorage.** No database or accounts are needed for one student practising.
  *Trade-off:* clearing browser data loses progress, and the page says so.
- **Browser test by hand, not in CI.** It needs Chromium and the 39 MB download on every run. CI checks
  the tasks themselves instead.
- **Make #33643's image tests run offline rather than leave them skipped** (team lead's choice, see
  below). The fallback, a Casebench-written test, wasn't needed.

## Problems found along the way

**1. A wrong fix for #33643 "solved" the task.** In review, the reviewer wrote a deliberately wrong fix
for #33643 (wrong numbers in a division). It passed all 9 required tests. The reason: 17 tests in
`test_image.py`, including the two that test the edited function, were *always skipped*. They need a
photo (SciPy's raccoon image) that scikit-learn downloads from the internet. In the browser there's no
download, so pytest quietly skipped them.
- **The choice:** a skipped test can't catch anything, so leaving them skipped wasn't an option. The team
  lead chose to make the image tests run offline, with a Casebench-written test as the fallback.
- **The fix:** an offline stand-in image. `runner.py` has an `offlineData` option, `"raccoon_face"`.
  For that run only, it sets the switch scikit-learn checks, provides an empty stand-in for the download
  library, and replaces `scipy.datasets.face` with a fixed, made-up 768×1024 image. Afterwards it undoes
  all three.
- The builder now records skipped tests in `task.json`. It refuses a task where a test is skipped on
  one side only.
- **Result:** #33643 now requires 4 fail→pass and 22 pass→pass tests, with 0 skipped. The reviewer's
  wrong fix now fails `test_reconstruct_patches_perfect` and `_perfect_color`.

> **Stand-in image note.** #33643's face tests use a synthetic image, not SciPy's raccoon photo. The task
> page says so: "These tests use a stand-in image instead of SciPy's raccoon photo, so they can run
> offline in your browser."

**2. The checker only re-ran its own list.** The first CI checker ran only the test ids written in
`task.json`. If someone removed a test from that list, the checker would run fewer tests and still be
green. And nothing tested the checker itself.
- **Fix:** it now runs the *whole* test file on "before" and on the fix, and works out the lists again.
  The fail→pass, pass→pass and skipped lists must match `task.json` exactly.
- It also checks that "before" plus `fix.diff` gives exactly the solution.
- `check-sklearn-tasks.test.ts` runs the real script on an intact copy (exit 0) and a broken one
  (exit 1).

**3. The `tests/` file wasn't tied to upstream.** Even the stricter checker trusted whatever test file
was in `tests/`. In the next review, the reviewer weakened #33643's tests to a shape check and used a
wrong fix as the "solution". The checker passed.
- **Fix:** the builder now writes `tests.diff`, the PR's real change to the test file. The checker
  requires `tests/` to equal scikit-learn 1.8.0's installed test file with `tests.diff` applied.
- The same attack now fails with "tests/... isn't the 1.8.0 test file + tests.diff".

**4. The stale-module trap.** Python remembers modules it has already imported (in `sys.modules`).
In a long-running worker, an edited scikit-learn file was silently ignored, and the old code ran. The
researcher saw #33643 stay at "4 failed" after the real fix until the modules were cleared.
- `runner.py` now clears every `sklearn` module before each run.
- It also writes no `.pyc` cache files, so a same-size edit in the same second can't run old code.
- The risk check proved it in the browser: before fails, the fix passes, before fails again, all in
  one worker.

**5. `packaging` made a fix look broken.** In research, PR #33491 showed 7 tests "still failing" with the
real fix. They weren't failing because of the fix: the error was `No module named 'packaging'`, a
package only the tests need. Lesson: run the real fix first, and treat leftover failures as an
environment problem until proven otherwise. (#33491 also needs pandas, so it isn't one of the five yet.)

**6. Accessibility gaps** (found in the review of steps 8–9, all fixed in `TaskWorkspace.tsx`):
- **The editor's name was in the wrong place.** Its `aria-label` (the name a screen reader reads) landed
  on a plain wrapper `div`, not on the part you type in. It now sits on the editable element, for both the student's file and the read-only tests.
- **Results were silent for screen readers.** A screen reader didn't hear anything when a run finished.
  An always-present "live region" now reads one sentence after each run, e.g. "86 of 87 required tests
  pass." or "Solved. All 87 required tests pass."
- **The pass/fail icons relied on a label on the icon itself.** The icons are now hidden from screen
  readers, and each test row starts with hidden text ("Passed:", "Failed:") that a screen reader reads.

The same review also found raw backticks showing in the text (now shown as code), a few error messages
that were slightly off, and a reset button that didn't clear old results.

**Also fixed in reviews:**
- **Mutation testing found two gaps.** The per-file checksum checks in `prepare-pyodide.mjs`, and the
  step in `runner.py` that puts the original file back, could each be deleted with all tests green.
  After the fixes, all 6 mutations tried are caught.
- **A timer could outlive the page.** It would start a new Python after the student had left. Run
  bookkeeping moved into `pendingRuns.ts`, which is tested.

### Known limits (said plainly)
- **Results checked in the browser can be faked.** Someone who knows the browser's developer tools can
  mark a task solved without solving it. That's acceptable while progress stays in the student's own
  browser. Trusted grading needs a server sandbox.
- **The real fix is in the page data before solving.** The app shows it only after solving, but it's
  sent with the page, so someone who looks can find it.
- **A 39 MB first load** (39.4 MB measured). It's cached after the first visit, with long cache headers,
  but a second visit with a warm cache wasn't measured.
- **Every task page starts a new Python.** It took 16.1 s, 16.9 s and 17.1 s in our runs, from a fresh
  browser profile. Moving between tasks means waiting again.
- **The PR and issue discussion text couldn't be fetched.** GitHub's PR pages and API are blocked from
  this sandbox. The context comes from what a `git clone` gives: commit messages, changelog entries,
  test changes and docstrings. `source.md` says so, and the page marks the issue link "couldn't fetch
  its text".
- **Not tested** in Firefox or Safari, over a real network (files came from localhost), or with a real
  screen reader (only the labels and live region were checked by script).
- **CI hasn't run on GitHub yet,** because the `casebench2` repo doesn't exist yet. The checker and the
  tests were run locally in the same way CI would.
- **Stuck on scikit-learn 1.8.0** until Pyodide ships a newer one.
- **Other tasks still have skipped tests** (#33127: 83, #33176: 33, #34815: 6, #33362: 5). They are
  recorded, and the checker requires the same list each time. Whether any of them exercises the edited
  code hasn't been written down task by task.

## Explain it in an interview
"Casebench 2's first track takes five real bugs that scikit-learn's maintainers already fixed. It lets a
student fix them in the browser and runs scikit-learn's own tests on their change, using Pyodide, which
is Python compiled for the browser. Before writing app code I tested the riskiest assumption, that
scikit-learn's tests even run in a browser, and measured it: 39 MB, about 16 seconds to start, and 2 to 5
seconds per re-run. The most useful bug was in the grading itself. A deliberately wrong fix passed,
because the tests that covered that function were silently skipped for lack of an internet download. So
we made them run offline with a stand-in image, and made the checker rebuild its expectations from
upstream's real test file instead of trusting its own list. The honest limit is that grading happens in
the student's browser, so it can be faked. That's fine for practice, and a server sandbox is the answer
when it has to be trusted."

## Teach-back
1. Why can a test that is *skipped* be worse than a test that fails?
2. What is the difference between fail→pass and pass→pass tests, and why does "solved" need both?
3. Why does SHA-256 pinning matter when the app downloads Python and scikit-learn?

<details>
<summary>Model answers</summary>

1. A failing test tells you something is wrong. A skipped test tells you nothing, and it still looks
   green. In #33643, the tests for the edited function were skipped because they needed an internet
   download, so a wrong fix "passed". We made them run offline with a stand-in image.
2. Fail→pass tests fail on the old code and pass with the fix: they prove the bug is gone. Pass→pass
   tests pass both times: they prove nothing else broke. A fix that only satisfies the first kind could
   still break other features, so "solved" needs both.
3. The app runs whatever files it downloads. Pinning compares each file's fingerprint with one written
   in our code and refuses any mismatch, so a changed or tampered file can't slip in. Every student
   gets exactly the same Python and scikit-learn that CI checked.

</details>
